# mikasa

把模糊的系统设计场景题变成一份「机制级回答 + 可交互手绘架构图 HTML」。

两条原则贯穿全文：

- **分水岭是中间产物。** 提到 Lua 就必须写出那段 Lua；提到表就必须给出建表 SQL；提到接口就必须给入参出参。没有中间产物的观点罗列就是 AI 味。
- **prose 只是引子，干货全部拆进图里。** 每一段「会死在哪儿/怎么解/权衡」都要找到它属于的那条连线或那个组件，写进对应的内容块。判断标准：用户不看 prose 只点图，也能拿到全部干货。

## 工作流

1. **先行推演（不输出给用户）**：对每个要写的问题，先写一段思考底稿——把因果链推演一遍（因为 A 所以 B 所以 C）、把原方案代码在脑内执行一遍找出它断裂的那一行。底稿是「分析」段的原料；没有底稿直接写 DSL，分析段必成「分析腔」。
2. **写 DSL**（语法见下），密度对齐 `examples/hongbao.dsl`——那是质量标杆。
3. **过 humanizer**：调用 `humanizer` skill（file mode，直接处理 DSL 文件）剥掉残留的 AI 腔。明确约束它：只改散文文本；DSL 结构行、缩进、``` 代码围栏里的内容必须原样不动。
4. **渲染验证**：`python3 <skill 目录>/render.py <dsl 文件> <输出.html>`，输出到用户当前目录。渲染器会强制校验 problems 结构——报错就回去补，不要绕过。humanizer 改完必须重跑一遍确认仍能解析。
5. **交付**：把 HTML 路径给用户（可直接 `open`）。图上点组件看实现、点连线看坑（现象/分析/解法三段呈现）、时序图在架构图下方整幅呈现。

## DSL 语法

````
case: 系统标题

prose: |                    # 可选，1-2 句引子，缩进 2 空格
  ……

comp 名字 [类型] @分组:     # 类型八选一：client/web/gateway/service/db/cache/mq/storage
  note: |                   #   @分组可选：同组组件被虚线框圈在一起
    ……                      # 内容块 key 缩进 2 空格，内容缩进 4 空格
  api: |                    # 块类型：note/api/lua/table/sql/logic 自由组合
    ……
  seq: 时序标题 |           # 时序图块（唯一支持标题的块），渲染在架构图下方
    用户 -> 网关: POST /grab      # -> 同步实线箭头
    Redis --> 网关: amount=3.21   # --> 虚线返回

edge A -> B [1.2]: 标签:    # [编号] 可选，不写自动按顺序编；尾部冒号必须有
  problems: |               # 结构化槽位：【问题名】+ 现象/分析/解法
    【问题名】              # 分析/解法必须各含至少一个 ``` 代码围栏，缺了渲染器报错
    现象: |
      ……
    分析: |
      ……（含 ``` 代码块：排查证据 + 原方案代码）
    解法: |
      ……（含 ``` 代码块：候选方案 + 选定方案）
  seq: 时序标题 |           # 连线也可以挂时序图
    ……
````

结构规则：

- comp/edge 顶格；块 key 缩进 2 空格；块内容缩进 4 空格。缩进错了渲染器会报行号。
- 每个 comp 至少一个内容块；每条 edge 必须有 `problems`。
- 组件和连线数量不设限——系统需要多少画多少；但只画核心链路，超过 8 个组件先问自己每个是否都在主链路上。
- 核心链路必须有一张 `seq` 时序图（挂在最关键的组件上）+ 主流程连线带编号 `[1.2]`，让读者一眼看出请求流向。
- `note` 块和 problems 槽位的文本里可以用 `围栏嵌入代码（开围栏可带语言标注，如`sql），会渲染成高亮代码块——先给代码再解释，不要把代码挤在散文里。
- 交互：点图标/连线 → 详情面板出现在架构图下方；再点一次或点空白处收起。

## 内容规范

### prose

1-2 句引子，只交代「这个系统的生死线是什么」。不写操作指引（「点组件看实现」是页面功能，不是内容），不写长篇论述——超出的内容拆开，找到它该去的连线/组件。

### 组件内容块：用代码说话

机制必须落到代码：`api` 块给入参出参和逻辑伪码；`lua`/`sql`/`table` 块给可直接读的真代码；`note` 块也先给伪代码/配置，再用完整句子解释 why。只有文字没有代码的说明，读者什么都学不到。

### 代码必须讲到能看懂

读者不预设懂这门语言、懂这个机制：

1. 每行非平凡的代码都要有注释，说清「这行做什么、为什么」。
2. 用到语言特有的语法（Go 的 select、信号量 channel、Lua 的 KEYS/ARGV），先用大白话解释这个语法本身的语义。
3. 代码之后跟一段完整的话，按一个请求的视角把执行流程走一遍。

解释宁长勿跳步——写长没关系，跳步才是罪。「令牌桶 rate=2000/s」这种配置罗列不是解释：要给出这段限流的实现代码，并交代 2000 这个数字怎么来的。

### 连线 problems：全文的灵魂

每个问题固定三槽位。**硬性校验**：缺槽位、或「分析」/「解法」缺代码围栏，渲染器直接报错，报错就回去补，不要绕过。

- **现象**：什么时候发生、谁受影响、后果是什么（有真实感的例子/数字）。
- **分析**：写成一线工程师的排查记录。从报警/用户反馈出发，沿请求链路一层层下钻；每一步先给出可执行的证据（access log 的一行、trace 的一个 span、metrics 的数值、慢查询报表的一条记录，用代码块呈现），再据此排除或确认嫌疑，进入下一层；最后配上原方案的代码，让读者亲眼看到病根在哪一行。直接跳到结论的「分析腔」会被拒；「看日志发现正常」这种纯文字口述观测也会被拒——证据必须落在读者能验证的形态上。
- **解法**：先给 2~3 个候选方案，数量与声称一致（写「候选有三个」就必须真的给三个），每个候选配实现代码 + 一句代价；然后选定一个，写明「为什么选它」——成本账、业务预期（这个系统里什么可牺牲什么不可牺牲）、复杂度，三条里至少一条。不比较就选型等于没想透，只给部分候选配代码也算没想透。

### 术语与措辞

- **黑话就地解释**：每个领域术语（连接池、正反馈、幂等、回源、水位……）第一次出现时，用大白话+具体数字说清楚它是什么、为什么会成为问题。写法模板：「网关到红包服务之间的 TCP 连接是从一个固定 200 条的池子里借的，借完不还新请求就得排队——这就是『连接池』」。判断标准：一个没做过这类系统的工程师读完不需要查任何名词。
- **性质词当场兑现**：声称「结构化/原子/幂等/高性能」时，当场贴出那个结构/那段代码（如「结构化」就要贴出 key 的四段拼法和反向解析）。
- **证据就地贴出**：「见 XX 组件」只能作补充指引，解法的关键代码必须就地贴出。
- **写完整句子**：让没做过这个系统的人也能读懂。

### 时序图

核心链路的时序图要详细到能复述请求的「一生」：不只画成功路径，关键分支（被限流拒绝、短路返回、快速失败、异步落盘、兜底对账）都要画出来；每条消息标清方法名/载荷/返回值，分支消息在标签里注明「分支：什么条件下发生」。一般不少于 10 条消息——只有 5、6 条说明分析得太粗。

## 反面清单

| 病灶             | 实例                                                                                   |
| ---------------- | -------------------------------------------------------------------------------------- |
| 总分总八股       | 「一、核心难点 二、整体架构 三、关键设计 四、总结」                                    |
| 只有观点没有产物 | 说「用 Lua 保证原子性」但不写 Lua；说「落 MySQL」但不出 schema                         |
| 无取舍           | 罗列 3 个方案不选；从不说「为什么不选 X」                                              |
| 无依据的量级吹嘘 | 「QPS 可达数十万」这种拍脑袋数字                                                       |
| 格式腔           | 每段小标题加粗、总结段「核心思路是…」、bullet 轰炸                                     |
| prose 长篇论述   | 超过 2 句的 prose——干货没进图就是写错了地方                                            |
| 电报体行话       | 「send 不 wait」「崩了可丢、跳转不能慢」——省略主语和推理，读者看不懂                   |
| 黑话不落地       | 「网关连接池耗尽后正反馈雪崩」——术语没有上下文，读者不知道连接池是什么、为什么会正反馈 |
| 配置罗列当解释   | 「限流：令牌桶 rate=2000/s」——怎么实现的？2000 怎么来的？读者照样一头雾水              |
| 代码不写注释     | 甩一段 Go select 信号量代码不解释语义——不懂 Go 的读者等于没看                          |
| 时序图太粗       | 核心链路只画 5 条消息的成功路径——拒绝分支、异步边界、兜底全丢了                        |
| 操作指引         | prose 里写「图上每个红标都能点」「点组件看实现」——这是页面功能，不是内容               |

## 常见错误

- DSL 缩进错：comp/edge 顶格，块 key 缩进 2 空格，块内容缩进 4 空格。渲染器会报行号。
- 忘记跑渲染器验证：DSL 写完必须跑一遍 render.py 确认解析成功再交付。
- humanizer 改坏 DSL：它动了结构行/缩进/代码围栏就会导致解析失败——重跑 render.py 报错时，优先回滚 humanizer 对非散文部分的改动。
